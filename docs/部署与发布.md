# Web/PWA 部署与发布

项目只构建一个静态网站，输出目录为 `dist/`。不要部署仓库根目录，也不要上传 `.env.local` 或 `local-backups/`。

## GitHub 发行包

GitHub Release 中的 `sixthings-web-pwa-<版本>.zip` 只包含静态网站及第三方许可证，不包含原生工程、本机凭据或测试适配器。通用发行包的后端配置为空，默认单机使用；开启同步前，按下面的顺序配置自己的 Supabase 并重新构建。`SHA256SUMS.txt` 用于核对下载文件。

上传源码和发行包不会执行数据库迁移。仓库可保持私有，网站部署独立进行。

## 同步 v3 升级顺序

1. 在旧版设置中导出一份清单备份，保存后端现有备份。
2. 在 Supabase SQL Editor 执行 `docs/supabase-schema-v3.sql`，保持匿名登录开启。
3. 配置构建环境变量 `SIXTHINGS_SUPABASE_URL` 与 `SIXTHINGS_SUPABASE_ANON_KEY`；本机也可使用被 Git 忽略的 `.env.local`。
4. 运行 `npm run check`、`npm test`、`npm run test:db`、`npm run build`。
5. 部署 `dist/`，在所有已配对设备上刷新页面；验证新增、删除、设置及离线重开后同步。

脚本建立新的房间、成员、邀请和幂等写入记录，不删除旧表。旧 v2 房间会在新版客户端登录后按原成员身份迁移到同一个 v3 房间。迁移后旧客户端对该房间的写入会被拒绝，必须刷新升级，避免两套数据继续分叉。旧版未成功上传且没有记录基线的删除无法自动推断，升级后需核对一次清单。

若遇到“同步服务需要升级”，先执行数据库脚本；不要把前端发布完成当作数据库升级完成。

## 托管设置

| 平台 | 设置 |
|---|---|
| Cloudflare Pages | 构建命令 `npm run build`；输出目录 `dist`；在构建环境配置上述两个变量 |
| Vercel | 仓库中的 `vercel.json` 已指定构建命令与 `dist`，在项目设置添加变量 |
| 自有静态服务器 | 上传 `dist/` 内容到 HTTPS 站点根路径 |

也可在完成构建后使用 Cloudflare Wrangler：

```sh
npx wrangler pages deploy dist --project-name <你的项目名>
```

部署凭据仅放在本机登录状态或 CI secrets 中。

当前 manifest 的 `start_url`、`scope` 为 `/`，适合独立域名或域名根目录；若使用 GitHub Pages 的 `/仓库名/` 子路径，需要同步调整 manifest 的作用域与启动路径。

## 缓存与版本

更新 `app.js` 的 `APP_VERSION`、`index.html` 中的版本参数和 `sw.js` 的缓存标识。`npm run check` 检查资源版本一致性。Service Worker 在首次完整加载后缓存离线资源，页面导航优先请求网络。

开发过程中若同一版本号下多次修改脚本，请刷新并确认新脚本已加载；发布时使用新版本号。`npm run build` 会清理并重建生成目录。

## 回滚边界

数据库脚本可重复执行。保留旧数据有助于核查，但已经迁移的房间不应只回滚前端到 v2；应修复 v3 或从明确备份恢复，避免覆盖迁移后的修改。

参考：[Supabase 数据库函数](https://supabase.com/docs/guides/database/functions)、[Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)、[Vercel 配置](https://vercel.com/docs/project-configuration/vercel-json)。
